# Стоимость вызова: что осталось сделать в обвязке

Список отсортирован по отношению «выигрыш / размер правки». Ничего из этого не
измерено на реальном профиле — это счёт вызовов по коду, а не бенчмарк. Первым
делом стоит померить (см. «Как мерить» в конце), потому что пункт 1 может
закрыть вопрос целиком и сделать остальные бессмысленными.

## Сколько сейчас стоит одна строка

`Session.ParseLine` на строке с N регионами делает:

- `colorer_alloc` + `Memory().Write` + `colorer_free` — 2 вызова в wasm и
  пара malloc/free внутри на каждую строку;
- `colorer_parse_line` — 1 вызов, собственно работа;
- **8 вызовов на каждый регион**: `start`, `end`, `name`, `fore`, `back`,
  `style`, `is_fore_set`, `is_back_set`;
- `readString` на имя каждого региона — чтение из линейной памяти по одному
  байту, с проверкой границ на каждый.

Строка JSON из тестов даёт 15 регионов. Это **больше 120 переходов Go→wasm на
одну строку** там, где хватило бы двух. Строка кода на C++ или Go — того же
порядка. Прокрутка экрана в 50 строк — порядка 6000 вызовов.

Для сравнения: батч-переякоривание, отложенное в HIGHLIGHT.md item 9, экономит
300 вызовов **на прыжок**. Пункт 1 ниже экономит столько же на **каждой
строке**.

## 1. Забирать регионы одним чтением памяти

`WasmRegion` — POD из восьми четырёхбайтовых полей (на wasm32 указатель тоже
четырёхбайтовый), то есть ровно 32 байта без выравнивающих дыр, и лежат они в
`std::vector` подряд.

Нужно: экспорт `const WasmRegion* colorer_get_regions(void* handle)`,
возвращающий `regions.data()`. В Go — одно `Memory().Read(ptr, count*32)` и
разбор `binary.LittleEndian` в цикле, без единого вызова в wasm.

Из 8N+1 вызовов на строку остаётся 2. Со стороны C++ это ~5 строк плюс
`static_assert(sizeof(WasmRegion) == 32)` и `offsetof`-проверки, чтобы правка
компилятора или флага не сломала разбор молча.

Имена регионов: указатели приходят из `name_cache`, ключ которого — `const
Region*`, поэтому для одного и того же региона указатель стабилен всю жизнь
сессии. Значит в Go достаточно `map[uint32]string`: `readString` вызывается
один раз на каждое уникальное имя за сессию, а не на каждый регион на каждой
строке. Имён в схеме десятки, строк — сотни тысяч.

## 2. Постоянный буфер под строку

`colorer_line_buffer(void* handle, int min_size)` — указатель на буфер сессии,
растущий по необходимости и живущий до `colorer_destroy`. Убирает
alloc/free-пару на каждую строку: минус 2 вызова в wasm и вся возня malloc.
Правка мелкая, риск близок к нулю.

## 3. Кэшировать `api.Function` в структуре сессии

Чисто Go-сторона, **пересборка wasm не нужна**. Сейчас каждый вызов начинается
с `s.mod.ExportedFunction("colorer_...")` — поиск по строке в мапе, в горячем
цикле по регионам он же повторяется 8N раз на строку. Разрешить все функции
один раз в `NewSession` и держать в полях.

Заодно: `api.Function.Call` аллоцирует `[]uint64` под стек на каждый вызов;
`CallWithStack` с переиспользуемым буфером в сессии это убирает. Сессия не
потокобезопасна по контракту, так что общий буфер безопасен.

Это единственный пункт, который можно сделать и выкатить, не трогая C++.

## 4. Только после замера: батч-скармливание строк

Вторая половина item 9 из HIGHLIGHT.md — «переякориться на строку X одним
вызовом». Смысл имеет ровно в том случае, если после пунктов 1–3 переход в wasm
всё ещё заметен в профиле. Если строка стоит 2 вызова вместо 120, то 300 строк
контекста на прыжок — это 600 вызовов на действие пользователя, и мерить там,
скорее всего, будет нечего.

Форму API по-прежнему стоит формулировать после пунктов 1–4 очереди HIGHLIGHT.md
в f4, когда станет видно, какая ширина окна реально нужна.

## Отвергнутое

**Считать атрибуты внутри wasm.** Технически убрало бы и разбор регионов, и
чтение имён: наружу шёл бы готовый массив атрибутов на строку. Но это переносит
в обвязку политику раскраски — соответствие регион → атрибут терминала, базовый
атрибут редактора, стили. Обвязка должна отдавать данные Colorer, а решать, как
они выглядят, — дело f4. Не делаем.

## Важное про измерение памяти

`ForgetBefore` (v0.1.12) возвращает память **аллокатору внутри wasm**, а не
операционной системе. Линейная память модуля не умеет уменьшаться — в wasm нет
операции, обратной `memory.grow`. Практический вывод для item 4 в HIGHLIGHT.md:
после прокрутки большого файла RSS процесса **не упадёт**, что бы обвязка ни
делала; упасть должна только скорость его роста, и держаться он должен на
плато вместо линейного роста с размером файла.

Мерить, соответственно, надо не «сколько RSS после», а «растёт ли RSS дальше,
когда прокрутка продолжается». Если после первых десятков тысяч строк рост
прекратился — подрезка работает, и item 4 (принудительное переякоривание ради
памяти) не нужен.

## Как мерить

Профиль стороны Go, на реальном файле, через f4 или через прогон `ParseLine` по
`far2l.s` в отдельном бенчмарке:

    go test -run XXX -bench . -benchtime 10000x -cpuprofile cpu.out
    go tool pprof -top cpu.out

Если верхние строки — `wazero` и `readString`, пункты 1–3 дадут ровно то, что
обещают. Если верх занят самим разбором внутри wasm, то всё вышеперечисленное
не стоит потраченного времени, и оптимизировать надо совсем другое.
